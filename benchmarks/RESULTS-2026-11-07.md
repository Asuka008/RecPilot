## Observed load curve

QPS counts successful completions **inside the 60-second window**. Success p99
excludes failed attempts. All-attempt p99 includes time until failure, not the
unobserved time a failed request would have taken to complete; it still excludes
client-dropped arrivals, which never reached the server.

| Mode / setting | Successful QPS | Success p99 ms | All-attempt p99 ms | Errors / attempts | Client drops / offered |
|---|---:|---:|---:|---:|---:|
| Closed / 1 workers | 238.05 | 9.57 | 9.57 | 0 / 14,284 | 0 / 14,284 |
| Closed / 4 workers | 243.58 | 30.51 | 30.51 | 0 / 14,619 | 0 / 14,619 |
| Closed / 16 workers | 211.57 | 36.11 | 2072.65 | 91 / 12,801 | 0 / 12,801 |
| Closed / 32 workers | 237.33 | 36.93 | 5005.28 | 290 / 14,537 | 0 / 14,537 |
| Open / 50 arrivals/s | 49.98 | 12.83 | 12.83 | 0 / 3,000 | 0 / 3,000 |
| Open / 100 arrivals/s | 99.98 | 13.10 | 13.10 | 0 / 6,000 | 0 / 6,000 |
| Open / 200 arrivals/s | 199.97 | 18.05 | 18.05 | 0 / 12,000 | 0 / 12,000 |
| Open / 400 arrivals/s | 193.87 | 3097.71 | 5002.03 | 134 / 11,790 | 12,210 / 24,000 |

At 200 scheduled arrivals/s all 12,000 requests eventually succeeded, with no
client drops and success p99 18.05 ms. This is an observed clean operating point,
not a proven safe production capacity. At 400 arrivals/s, 24,000 arrivals were
scheduled, 12,210 were dropped by the client, 11,790 attempted and 11,656
succeeded. Eventual success was 48.57% of offered load. Successful window QPS
fell to 193.87; including the 65.99-second drain window it was 176.62 QPS.
These client drops are not server 429/503 responses or evidence that 400 QPS
actually reached the server. Under overload the attempted workload can differ
from the full request mix because blocked arrivals are omitted.

Closed concurrency 4 reached 243.58 successful QPS with no errors. Concurrency
16/32 did not produce proportional throughput, and introduced 0.711%/1.995%
request errors. The highest observed successful window rate was 243.58 QPS;
this is not an exact hardware throughput ceiling or an established SLO capacity.

The closed-32 success-only p99 of 36.93 ms hides slow failures: all-attempt p99
was 5,005.28 ms. The 400-arrivals/s run already has a success p99 of 3,097.71 ms
and an all-attempt p99 of 5,002.03 ms. Reporting success latency alone would be
misleading. Client dispatch lag p99 at 400/s was only 3.15 ms among attempted
requests; this does not explain the multi-second response tail, but cannot
rule out all client-side/network contributions.

## Failure interpretation

Errors were TimeoutError / ConnectionResetError: 89/2 (closed 16), 258/32
(closed 32), 113/21 (open 400). All error rows have no received HTTP status;
none are a recorded model-contract validation error or an explicit overload
HTTP rejection. This does not rule out server failures before a response.

The returned server BrokenPipeError log is consistent with writing a response
after a client disconnects. The service uses serial HTTPServer, and the client
creates new connections. Connection admission/backlog, request processing and
response delivery may all contribute. The reports do not separate connect,
server queue, inference and response times, so they do not identify which
network phase timed out, nor prove that GPU computation saturated. No per-request
correlation IDs were recorded to pair individual disconnects with client errors.

The configured five seconds is a socket operation timeout, **not an end-to-end
request deadline**. Successful requests can therefore exceed five seconds; the
open-400 maximum successful duration was 8.184 seconds. This refines the earlier
informal description of a "five-second client timeout". Raising that timeout
or suppressing BrokenPipe logs would not by itself improve capacity.

Python references: [synchronous server behavior](https://docs.python.org/3.11/library/socketserver.html),
[socket timeout semantics](https://docs.python.org/3.11/library/socket.html#socket.socket.settimeout),
[BrokenPipeError](https://docs.python.org/3.11/library/exceptions.html#BrokenPipeError).

## Operator evidence

Both supplied CPU-self-time-sorted `operators.txt` files were inspected. Labels
and call counts identify ten serving requests and ten training steps, consistent
with the respective capture configurations. The text files do not embed a run
ID; their association uses the supplied context and observed labels. Full raw
trace timelines have not been inspected.

| Operator count in ten profiled iterations | Serving | Training |
|---|---:|---:|
| cudaLaunchKernel | 1,510 | 6,707 |
| cudaStreamSynchronize | 100 | 400 |
| aten::_local_scalar_dense | 70 | 550 |
| aten::isfinite | Not in displayed top 60 | 210 |

Many small launches and scalar/synchronization operations support investigating
host dispatch and synchronization overhead as well as kernel work. They do not
prove that all scalar reads synchronize CUDA, or that eliminating checks is safe.
The training finite-check calls correspond to the current safety-heavy reference
path; any optimization must retain finite-loss/gradient/update detection.

Serving self CUDA sum was 5.065 ms over ten requests; training 36.479 ms over ten
steps. These are profiler aggregates, not uninstrumented end-to-end latency or
GPU utilization. CPU totals include instrumentation and can include work across
threads; nested CPU-total rows must not be summed. Backward wrapper CPU time
is not an attention-only cost. The trace sample is short, and profiler overhead
precludes projecting a speedup from these numbers alone.

## Completion and next experiment

The first milestone is complete as an **initial baseline**: core timings,
diagnostic attribution, operator tables, HTTP load curves and overload outcomes
are available. It establishes neither production readiness nor a repeated-run SLO.
No serving/model implementation was changed during this review.

The next proposed change is a bounded serving scheduler with request deadlines,
explicit overload responses, disconnect accounting, and separate queue/inference
measurements. Keep one managed GPU execution path; add controlled microbatching
as a distinct ablation after single-request parity. Compare old/new service on
the same corpus, client connection policy and arrival grid, including failures
and client drops; repeat relevant operating points and report load recovery.
Do not select a different model or change frozen ranking/fusion semantics.
Caching static candidate representations and reducing redundant dispatch are
subsequent measurable hypotheses. No evidence yet makes FSDP the priority.
