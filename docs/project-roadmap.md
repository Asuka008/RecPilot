# 项目方向与决策记录

更新日期：2026-10-22。实现与服务器验证分开记录；历史阶段已完成的状态以本页及 README 的最新记录为准。

## 项目定位

构建可复现、可解释实验结论的 HSTU 视频推荐项目，用于工业界推荐算法与
机器学习工程岗位。场景是根据用户历史自动推荐视频，不要求用户输入自然语言需求。
保留 AgenticRec 仓库名，但 agent 不再是必需组件。

项目的辨识度来自一个完整过程：发现数据或模型的问题，建立可信对照，验证
针对性改进，并测量工程成本。标题融合、复杂门控、多模态、强化学习都不是预定成果。

## 已确定的选择

| 议题 | 当前决定 | 原因 |
|---|---|---|
| 主模型 | HSTU | 有工业部署依据、官方公开实验和持续发展的工程生态 |
| SASRec | 完整复现可选 | 复用已有 Dataset，不将另一个模型的实现设为前置条件 |
| 基础对照 | Popularity、ItemCF | 确认复杂模型的价值，并验证统一评估器 |
| 标题 | 作为待检验的信息来源 | 行为 embedding 已可能隐式编码语义，文本增益必须实测 |
| Agent | 移出当前范围 | 尚未找到超出普通模型或固定规则的必要作用 |
| 更近期模型 | 阅读参考 | MTGR、OneRec、OpenOneRec、PinRec 不增加为实施里程碑 |
| 运行环境 | 服务器验证模型与性能 | Mac 用于编辑、预处理和轻量确定性检查 |

HSTU 的公开数据配置见 [Meta 官方仓库](https://github.com/meta-recsys/generative-recommenders#experiments)。
[NVIDIA 官方示例](https://github.com/NVIDIA/recsys-examples)提供训练和推理实现，
但其完整依赖栈不等于本项目第一版所需范围。先选定版本、验证兼容性，再接数据。

较新的工业工作并不都适合直接替换当前骨干：
[MTGR](https://arxiv.org/abs/2505.18654)基于 HSTU，重点包含交叉特征；
[OneRec](https://arxiv.org/abs/2506.13695)覆盖更广的端到端系统与强化学习；
[PinRec](https://arxiv.org/abs/2504.10507)使用多场景行为及曝光数据。
[OpenOneRec](https://github.com/Kuaishou-OneRec/OpenOneRec)是相关开放基础模型项目，
不能直接等同于复现 OneRec 的线上系统。

## 数据告诉我们的事

当前有 50,000 个用户、19,220 个物品、359,708 条交互。完整序列平均长度
7.19416，中位数 6，P99 为 24。因此暂不把超长序列加速作为主贡献。

18,490 个物品在训练历史中出现过，其中 6,970 个只出现 1–5 次。
另外 730 个物品未出现在任何训练历史中；它们对应 844 条验证样本和
2,226 条测试样本，分别占 1.688% 和 4.452%。这是值得诊断的问题，
并不是文本融合必然有效的证据。

这 730 个物品不能直接称为真实新发布视频：目前未检查发布时间与内容可用时间。
它们没有训练历史中的正向交互，但仍可能作为损失中的候选或负样本出现。
标题覆盖率为 100%，只能证明可连接，不能证明标题准确、信息充分。

## 建议增加的诊断思路

以下是本次整理提出的实验建议，需在纯 ID HSTU 跑通后实施。

### 先确认序列建模带来了什么

增加一个很小的神经对照：有效历史物品 embedding 的平均池化，再使用与
HSTU 一致的候选表示、打分方式、损失和评估。用相同数据与调参预算比较，
同时报告参数量和耗时，避免把它称为严格隔离全部架构因素的实验。

在短历史上，这能判断复杂编码是否带来实际收益。它不自动证明收益来自
顺序；若进一步测试顺序，应先构造每个预测时刻的可见前缀，再只在前缀内部
改变顺序。不能先打乱完整序列再生成移位标签，否则未来目标可能进入输入。

### 将物品反馈不足与用户历史不足分开

主要结果分为两种切片：用户可见历史长度、目标物品训练频次。
频次初始分组建议为 0、1–5、6–20、21+，每组同时报告样本数，阈值在看
测试结果前固定。两个切片可交叉观察，但小样本格子的结论要谨慎。

如果收益集中在零频或低频目标，再验证标题初始化或简单融合；如果平均池化
与 HSTU 相近，先检查数据与训练目标是否支持复杂序列建模。不要先承诺改进形式。

### 用最低成本验证语义是否提供额外信息

可选实验顺序为：纯 ID → 标题初始化 → 固定融合 → 频次相关融合。
固定文本编码器并缓存向量；当前先用训练物品 PCA 固定降维，后续再视证据考虑可训练投影。历史输入和候选打分要使用明确、
一致的物品表示定义。文本缺失、无意义标题的回退也属于方法的一部分。

频次仅是反馈充分程度的代理，不能直接称为可靠的置信度。简单方案有效后再
考虑可学习门控。采用相同调参预算、多个种子，并以验证集决定是否保留模块；
训练更多轮不会产生新的独立交互证据。

## 实施顺序与完成标准

1. **数据与服务器检查。** 比对数据校验值，服务器通过现有 8 个 Dataset 测试。
2. **共享评估与简单基线。** 实现 Recall/NDCG@10/20，用手算样例核对；
   Popularity、ItemCF 只能使用训练历史，生成带配置与数据标识的结果。
3. **纯 ID HSTU。** 固定上游版本和配方，先验证一个小规模官方公开实验，
   再迁移 MicroLens。完成因果/padding 检查、小样本拟合、有限梯度与检查点恢复。
   数值容差、官方指标差异及任何配方改动必须记录。
4. **一个有依据的改进。** 用分组指标和简单神经对照定位问题，选择一个假设，
   完成消融、多种子比较和成本测量。负结果也记录，不预设标题必须有效。
5. **可运行的推荐服务。** 先做精确打分、历史过滤、模型版本管理与回退。
   如引入近似检索，报告其相对精确 Top-K 的召回损失及延迟变化。

每个实现里程碑应有代码、配置、验证命令、教学笔记和实际结果。ML-1M 结果来自用户回传的服务器输出；用户已回传 MicroLens 的 33 个服务器测试及三轮短训练 PASS；本地未直接访问服务器产物。

## 评估边界

- 首版沿用逐用户 leave-one-out。它保证自身目标不进入历史，不保证不同用户
  之间满足同一个全局时间截止点。以后做时间回放时，新建版本化协议。
- 候选集合使用完整映射目录，显式假设该目录预先已知。排除 padding 和当前
  用户完整可见历史，定义稳定的同分排序；零训练频次目标保留并单独报告。
  当前审计没有历史重复目标；以后若出现，应单独定义允许复看的协议，不能
  静默删除样本或依据目标临时修改过滤规则。
- 标题预计算不应使用验证/测试交互训练文本投影或融合策略。严格时间实验还需
  确认标题在推荐时已可用，不能把交互日志首次出现时间视作已知发布时间。
- 未交互候选不是可靠的曝光负例。当前数据不能支持线上 CTR、观看时长或
  因果收益声明；覆盖率提高也不等同于用户满意度提高。
- 训练与服务性能必须报告实际设备、精度、批量、候选规模、预热及并发条件。
  H200 结果不能由 Mac 或 A100 结果代替。
